## 0. 修订说明（2026-10-22）

本版根据仓库历史数据修正了初版的三个问题：

| 初版问题 | 修订 |
|---|---|
| 用“传统人日”估算，与项目实际节奏差一到两个数量级 | 改用**工作时段**为单位，基准取自 cube 地基的真实交付节奏 |

## 1. 当前项目估计

### 1.1 结论

**项目是一个功能覆盖很广、可玩的开发版；剩余工作的 70% 以上集中在“把已有 cube 地基变成正常游戏唯一路径”这一件事上，而不是缺功能。**

判断依据不是主观印象，而是已完成地基 vs 待改消费面的量化对比：

| 观察项 | 实测 | 含义 |
|---|---:|---|
| cube 地基生产代码 | 2253 行 | 坐标、姿态、几何、覆盖、生成、存储、队列、投影网格齐备 |
| cube 地基测试代码 | 1924 行 | 原语级覆盖充分 |
| 待改的 `GetBlockAt` 调用点 | 76 处 / 23 个文件 | 消费者仍按 map 坐标取方块 |
| 待改的地形高度查询 | 62 处 | `TerrainHeight` / `PlanetTerrainHeight` / `WorldSurfaceHeightAt` 仍按 map 坐标 |
| 玩家/交互/流式核心文件 | 712 / 751 / 1431 行 | 坐标语义改造的真正成本所在 |
| `SurfacePose` 生产调用者 | 0 | 连续姿态只有原语，无人使用 |
| `ChunksUpdateCubeCoverage` 调用者 | 0（仅测试与自身） | 正常 `UpdateChunks` 仍走 map 正方形枚举 |
| V30 实现 | 0（仅文档提及） | 存档侧完全未动工 |
| cube 路径的 CGA / 流体接入 | 0 | 结构生成与流体仍绑旧网格 |

### 1.2 分维度估计

沿用[进度报告的五维口径](project-progress-2026-10-20.md#L37-L51)，给出区间而非单值：

| 目标范围 | 功能实现 F | 生产集成 I | 正确性 C | 性能 P | 验收 V | 综合判断 |
|---|---:|---:|---:|---:|---:|---|
| 当前开发版（旧网格主线） | 0.85 | 0.80 | 0.75 | 0.45 | 0.55 | 可玩；图形/性能/发布级证据缺 |
| cube 激活目标 | 0.60 | **0.20** | 0.55 | 0.30 | 0.25 | **瓶颈是集成**，不是实现 |
| 项目整体（当前承诺范围） | 0.80 | 0.60 | 0.65 | 0.45 | 0.50 | 见下方说明 |

**为什么 cube 的 F 给 0.60 而不是 1.0**：12 项验收台账中 7 项已实现（CG-01～CG-07），1 项部分（CG-08），4 项未完成（CG-09～CG-12）。按项数约 58%；但**按工作量，剩余 4～5 项占激活工作的 70%～75%**，所以不能按项数理解进度。

**为什么 P 和 V 普遍偏低**：本次只跑了普通 CPU 回归（120 通过 / 0 失败），没有 Sanitizer、图形 E2E、极区画面、受控性能基准和覆盖率。这与实现质量无关，是证据缺口。

### 1.3 估算基准：为什么不用“人日”

初版用人日估算，但仓库数据显示这个基准不适用：

| 日期 | 提交数 | 代码量 |
|---|---:|---|
| 2026-10-03 | 44 | 14,754 行 |
| 2026-10-08 | 9 | 3,837 行 |
| 2026-10-14 | 3 | 1,646 行 |
| 2026-10-20 | 18 | 6,101 行（含完整中式院落 + 场景工具） |

项目总计约 **106,870 行生产代码 + 45,959 行测试**，分布在 35 个活跃日。

最关键的校准是 **cube 地基本身**：4,177 行（含 1,924 行测试）只跨越 **3 个工作时段**：

| 时段 | 日期 | 内容 | 产出 |
|---|---|---|---:|
| S1 | 10-07 | 跨面邻接 + 极区测试 | 520 行 |
| S2 | 10-08（3 个 commit，跨度 1.5 小时） | 连续姿态、地形暂存、拓扑 + V29 | 2,606 行 |
| S3 | 10-14（3 个 commit，跨度 2.5 小时） | 生成队列、编辑、覆盖 + 网格 | 1,646 行 |

**因此本计划改用“工作时段”估算**：一个时段 = 一次集中开发，产出约 500–2,600 行含测试的改动。这不预设一天还是几小时——它只描述“一次能完成一个内聚单元”。

换算参考：初版的 76–122 人日，在项目实际节奏下大致对应 **15–30 个工作时段**。这个数字仍仅供参考，因为剩余工作（尤其 W3）的**认知密度**高于地基：地基是新增独立模块，W3 是改造既有 8,000+ 行的耦合代码，单位产出会低。

### 1.4 估计的不确定性

- 剩余工作的主要不确定性来自 W3（消费者统一）：地基是写新代码，W3 是理解并改写已有语义。
- 76 处调用点不等于 76 处改动，但**每一处的坐标语义都要重新推理**，不能机械替换。
- 若 cube 投影需要改为等角/低畸变，W1/W3 的几何部分需要返工。
- 已确认放弃双轨并存，因此不保留“只做一半”的退路；这也意味着 W2（V30）一旦开始就无法半途回到 V29 世界。

### W1a 极区独立修复 — **已撤销（2026-10-22 实测否决）**

计划书初版认为极区窄条主要是候选枚举造成的，可以先独立修好。**实测证明这个前提是错的，W1a 不再执行。**

**计算结论**（基于 `SURFACE_EQUATOR_BLOCKS = 16384`、`SURFACE_RADIUS_BLOCKS ≈ 2607.6`）：

- legacy map 网格的**每一圈纬度固定是 1024 个区块**，与纬度无关。
- 越靠近极点，一圈的物理周长越小：距极点 16 块时，整圈只有约 100 块长，单个区块宽约 **0.098 块**。
- 要铺满半径 16 块的地面，一圈就需要约 1024 个区块；半径 32 块需要 2048 个——**全部超过 625 的槽位预算**。
- 当前枚举在极点得到的是 **0.23 块宽 × 400 块高**的区域，长宽比约 **1736:1**，这正是截图里那条窄竖条。

**任何渲染距离都无法修复**（该表随距离平方增长而覆盖宽度只线性增长）：

| 渲染距离 | 槽位 | 极点实际覆盖 |
|---:|---:|---|
| 12 | 625 | 0.23 × 400 块 |
| 64 | 16,641 | 1.19 × 2,064 块 |
| 256 | 263,169 | 4.73 × 8,208 块 |
| 1024 | 4,198,401 | 18.9 × 32,784 块 |

**因此**：极区窄条不是枚举 bug，而是 **legacy 经纬网格无法表示极点附近地面的结构性缺陷**。用 map 坐标重写候选枚举只会改变窄条的宽度，不会消除它。

**对计划的影响：**

1. 极区视觉验收**不能**作为 cube 迁移之外的独立里程碑，它本身就是迁移要解决的问题。
2. cube-grid 用立方体六面划分，极点落在面内部而不是坐标奇异点，因此能从结构上消除该缺陷——这正是迁移的核心价值之一。
3. 原 G-a 里程碑取消。W4 的极区验收保留，但它验证的是 cube 路径，而不是旧网格。

**保留的正确判断**：候选枚举确实是一个独立的健壮性问题（它按 map 环距而非物理距离排序），但它不构成极区修复方案。若将来要改善旧网格的加载优先级，可作为独立小项，不影响迁移主线。

## 3. 阶段计划

### 3.1 顺序与依赖

```text
W0 契约冻结（决策 + 文档，1 个时段）
   │
   └─▶ W1 最小闭环 ──▶ W2 持久化 ──▶ W3 消费者 ──▶ W4 覆盖/性能 ──▶ W5 收口
            │              │              │              │
            └──────────────┴──────────────┴──────────────┘
                  每阶段结束：单测 + 架构 + 聚焦 e2e + 单独 commit
```

**串行理由**：W1 确定身份与几何契约，W2 才能定序列化；W3 的每个消费者都依赖 W1/W2 的地址语义；W4 只能在消费者统一后测真实负载。提前并行会把同一处返工做多次。

**极区不在独立路径上**：W1a 已被实测否决（见第 2 节）。极点窄条是 legacy 经纬网格的结构性缺陷，只能由 cube 迁移本身消除，因此它不是并行里程碑，而是 W1–W4 要交付的结果之一。

### 3.2 里程碑与判定点

| 里程碑 | 判定内容 | 不通过则 |
|---|---|---|
| **G0** | W0 四张表一致，文档无 v8 类错误 | 不进入 W1 |
| **G1** | 单星球跨接缝/角点可走、可挖、可返回 | 回退 W1，不并行 W3 |
| **G2** | 跨面编辑经**重启进程**仍一致；坏档拒绝且不损原文件 | 不进入 W3 |
| **G3** | 流体/生态/CGA/火山在 cube 下行为一致且有回归 | 逐项回退，不进入 W4 |
| **G4** | cube 路径下的双极/面边/高空视觉通过；性能在预算内 | 不进入 W5 |
| **G5** | 同一提交全门禁通过，证据可重放 | 发布候选不成立 |

G1 和 G2 是**不可跳过的硬门槛**，也是估算校准点：跨过 G2 后重新校准 W3/W4 的估计，之前的数字只作参考。

### 3.3 每阶段的统一交付物

1. 代码 + 聚焦单测（新行为必须有边界和失败路径用例）。
2. 架构检查通过；无跨组件私有头依赖。
3. 对应 DSL 诊断字段（缺功能按 AGENTS 扩展 DSL 并更新 `docs/debug-dsl.md`）。
4. 若涉及画面，附截图与同名 `.txt` 报告，写明 HEAD、命令、退出码。
5. 一个独立 commit，消息格式 `area: lowercase imperative summary`。
6. 更新阶段记录；**失败或未复现的尝试必须写明**。

## 4. 风险与应对

| 风险 | 触发信号 | 应对 |
|---|---|---|
| 坐标语义半迁移 | 同一方块在画面/碰撞/存档中不一致 | 单一入口 + 转换集中；禁止在两套坐标间隐式转换 |
| 隐藏耦合爆炸 | W1 中后期改动点持续增长 | G1 前冻结接口；超出预算 30% 时暂停并重估，而不是硬推 |
| 投影畸变不可接受 | 建筑尺度或移动手感异常 | 在 W0 做小样本对照；只有数据支持才改投影，避免同时换拓扑 |
| 覆盖饱和被当作就绪 | 极区/高空缺地面但 `surface_ready` 为真 | 分离 requested/admitted/ready；把饱和当作一等状态 |
| 存档污染 | 试验 cube 状态写进 V29 | 实验隔离；未过 G2 前不写任何 cube 数据到世界档 |
| 性能回归 | 帧时间或内存超预算 | 冻结场景/worker/距离；同机三次基准；不以“感觉流畅”验收 |
| 文档再次滞后 | 出现 v8/v9 混淆 | 每阶段同步当前状态入口，历史记录加指向新边界的说明 |

## 5. 现在不建议做的事

以下都会推迟主线，且不能替代当前收口：

- 扩展全球气候/海洋/板块等需要跨区状态的模型。
- 布娃娃、块图坍塌、完整生存需求的生产化。
- 新增建筑风格或更多独立系统。
- 为“更先进”提前替换 cube 投影或整个拓扑。
- 在 G2 之前大规模改造生态与建筑生成。

它们不是永远不做，而是**不应插在 W1–W2 之前**。

### W1 的关键发现：两种网格的方块身份不能一一对应

测试支架补齐后，用真实投影测量了 legacy map 坐标到 cube 单元的映射：

| legacy map 位置 | 映射到 cube 单元 |
|---|---|
| (0.5, 0.5) | face 0, u=2047, v=2047 |
| (100.5, 200.5) | face 0, u=1969, v=1890 |
| (4090.5, 0.5) | **face 4**（跨面跳变）|
| (0.5, 4090.5) | **face 2**（跨面跳变）|

原因是两套网格的划分方式不同：

- legacy：赤道方向 4 个面，每面 4096 个 map 单元；单元物理宽度随纬度收缩（赤道 1.0 块，45° 0.707 块）。
- cube：6 个面，每面 4096 个单元；单元在面内近似等大，只在角部形变。

**因此 legacy 的一个方块和 cube 的一个方块不是同一个东西，无法用坐标转换保持身份。** 这不是实现细节，而是两个网格的定义差异。

**对 W1 的影响**：

1. 不能做“保留地形、只换坐标解析”的渐进切换——那会让同一地形在两套网格下产生不同的方块身份。
2. W1 必须包含**生成器切换**：地形按 cube 面重新生成，旧地图编辑不迁移（与“V30 不迁移 V29”的既定契约一致）。
3. 玩家、碰撞、选取的改造必须与生成器切换同时落地，否则会出现“看得见但踩不到”的区块。

这解释了为什么 W1 是整条计划里最重的一步，也说明原计划把它排在 W2 之前是对的。

### 为什么 W1 仍未动手

上一轮撤回的 `SurfacePose` 互转尝试，本质是在假设“两种网格可以转换”。现在测量证明这个假设不成立，因此该方向被放弃，W1 需要按“生成器切换 + 消费者同时切换”重新设计，而不是坐标适配。

本轮补齐了它的前置条件（测试支架带表面上下文），但 W1 主体需要独立的完整设计，不能在一轮内仓促拼接。
