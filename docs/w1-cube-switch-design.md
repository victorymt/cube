# W1 设计：cube 生成器原子切换

- 状态：**设计稿**，2026-10-22，基线 `d8f5208`
- 依赖：[激活契约](cube-contract.md)、[激活计划](cube-activation-plan.md)
- 结论先行：**切换必须整体发生，不能分片。半迁移状态是可玩性事故，不是可接受的中间态。**

## 1. 为什么不能做坐标适配

上一轮用真实投影测量证明：legacy 与 cube 的方块身份不能一一对应。

| | legacy map | cube grid |
|---|---|---|
| 面数 | 赤道 4 面 | 6 面 |
| 每面单元 | 4096 map 单元 | 4096 单元 |
| 单元宽度 | 随纬度收缩（赤道 1.0，45° 0.707） | 面内近似等大，角部形变 |

同一个 legacy 位置 `(4090.5, 0.5)` 会映射到 **face 4**，而 `(0.5, 4090.5)` 映射到 **face 2**——面边界直接跳变。

**推论：** 任何“保留已有地形、只把坐标解析换掉”的方案，都会让同一批方块在两套网格下得到不同身份。因此 W1 只能是**生成器切换**，旧地图编辑不迁移（与“V30 不迁移 V29”一致）。

## 2. 当前的实际阻塞点

cube 路径今天完全没有入口，三处硬拒绝：

| 位置 | 行为 | 后果 |
|---|---|---|
| `WorldSurfaceTopologyPolicyIsSupported` | 只接受双 legacy-map | cube 策略装不进去 |
| `WorldInstallSurfaceSnapshot` | `SurfaceTopologyIsRuntimeSupported` 拒绝 cube-grid | cube 快照装不进去 |
| `UpdateChunks` | 只枚举 map 正方形 | 从不调用 `ChunksUpdateCubeCoverage` |
| `TerrainCubeContextCreate` | **生产代码零调用** | cube 生成器从未启动 |

注意：这些拒绝本身是正确的保护，不是缺陷。它们保证 legacy 世界不会误入 cube 路径。切换要做的是**在受控条件下解除**，而不是删掉。

## 3. 切换的原子性边界

一次切换必须在同一个操作内完成，中间不允许游戏帧运行：

```text
1. 排空            DrainChunkGen + UnloadAllChunks + UnloadAllSpaceChunks
2. 重建快照        GameSyncWorldSurfaceSnapshot 带 cube 拓扑
3. 重建生成上下文  TerrainCubeContextCreate（捕获地形版本）
4. 重置依赖状态    编辑器、撤销栈、流体队列、生态、火山水文区域
5. 安放玩家        选一个有效 cube 单元，落到地表
6. 首次覆盖        ChunksUpdateCubeCoverage 直到 min 就绪
7. 提交            只有 6 成功才对外可见；失败回滚到旧拓扑
```

**关键：** 第 7 步之前，任何失败都必须能回滚。若第 6 步超时，应保持“加载中”而不是放玩家进空世界。

## 4. 状态清单：谁要在切换时重建

| 状态 | 归属 | 切换动作 |
|---|---|---|
| 表面快照 | app | 用 cube 拓扑重建 |
| cube 生成上下文 | world | 新建（捕获地形 11） |
| 区块池 625 槽 | world | 全部卸载，槽位复用 |
| cube 编辑存储 | world | 清空（不迁移旧编辑） |
| 撤销历史 | world | 清空 |
| 流体队列 | world | 重置 |
| 辐射/水文运行时 | world | 全局重置 |
| 生态区域缓存 | ecology | 保留容量，按新 body 重绑 |
| 火山水文区域 | app | 重置 |
| 玩家姿态 | gameplay | 重新落点 |
| 存档格式 | app | V30（未完成） |

## 5. 玩家侧：必须先有可见的落地判定

切换后玩家位置必须满足：

1. 落在某个 cube 单元的实心地面上（`WorldCubeBlockAt` 非空）；
2. 上方两格为空气；
3. 不触发 `PlayerOverlapsWorld`。

这需要一个**只用 cube 身份的落地查询**。上一轮已实现 `WorldBlockBoxCollect`，可复用来判断占位。

## 9. 移动尺度的实测结论（2026-10-22）

尝试把 legacy 移动改成按物理块推进时，实测数据推翻了原假设。

### 可靠测量

16 个东向 map 格的弧长随纬度收缩，这是可重复的：

| mapZ | 16 格东向弧长 |
|---:|---:|
| 0 | 14.62 块 |
| 1024 | 16.03 块 |
| 2048 | 15.13 块 |
| 3072 | 11.70 块 |
| 3584 | 0.00 块 |
| 4096 | 0.00 块 |

### 不可靠的测量

**单格宽度不能用。** 投影是量化的，一格步进可能两次落在同一位置：

- 单格测量在多数纬度读数为 0.90，在极点读到 0；
- 同一纬度下沿 longitude 取样，读数在 0.28–1.02 之间波动（3.6 倍）。

一个按位置取标量的缩放无法表达这种经度方向的波动，因此该方案**未通过验证**，代码已回退。

### 与极区缺陷的关系

mapZ ≥ 3584 时东向弧长为 0，意味着该处所有 longitude 映射到同一物理点。**这与第 2 节记录的极区结构性缺陷是同一个问题**，不能靠移动缩放修复。

### 对 W1-3 的结论

移动改造不能建立在“每格有稳定宽度”的假设上。正确做法是让移动**完全使用 `SurfacePoseDisplace` 的物理位移**，只把结果写回时走一次投影，而不是在 map 格空间里做缩放。这需要先把玩家的权威位置改为 `SurfacePose`（原 §5 已列出），属于同一批改动，不能拆开。

## 10. 流体不能在 cube 上运行的准确原因（2026-10-22 修正）

第 13 轮曾把原因写成"不同 face 的相同 `(u,v)` 共用桶"。这个说法**不准确**，
下面重新推导了真实原因。

### 写路径与读路径不在同一坐标空间

| 路径 | 键的来源 |
|---|---|
| 写入 bucket | `cx = FloorDivInt(edit->x, CHUNK_SIZE)`，`edit->x` 是**世界坐标** |
| 应用 edits | `cx = chunk->cx`，legacy 区块是 map 区块索引 |

在 legacy 网格上两者一致，因为 `WorldToChunkLocal(worldX)` 就等于
`floor(worldX / 16)`。

在 cube 网格上不一致：cube 区块的 `cx = key.u`（面内 0..255 的局部格），
而 edits 仍按世界坐标分桶。两者是**不同的量，没有理由相等**。

### 还有一处更根本的失败

`FluidLocateCell` 通过 `WorldToChunkLocal(x, z) -> FindChunk(cx, cz)` 找区块。
`FindChunk` 只搜索 legacy 索引；cube 区块按 `cubeKey` 存放，**永远找不到**。

因此流体在 cube 世界的失败不是偶发的桶冲突，而是**必然无法定位任何区块**。

### 结论

第 13 轮"在 cube 下停用流体"的处置是对的，但理由是上述两点，不是 face 撞桶。
真正启用需要把 fluid 的定位与分桶都改成 cube 键，工作量远大于"加一个 face 字段"。
