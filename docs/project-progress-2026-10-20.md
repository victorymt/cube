## 1. 执行摘要

**项目已具备内容丰富的可玩开发版基础，但新球面网格的主线集成与整体验收尚未收口。当前不能据此认定已经达到稳定发布质量。**

主要结论：

1. 基础沙盒、太空与行星探索、天气灾害、区域生态、火山和程序化建筑均已有实际代码；其中多数已有正常游戏接线，不只是接口或演示。
2. cube-grid 的坐标、生成、存储、任务队列、物理覆盖和网格投影已有实现；正常游戏默认仍为 legacy-map/1。玩家、流体、生态、存档及极区视觉验收没有完成统一转换。
3. 当前地形生成器版本为 **11**，当前世界存档格式仍为 **V29**；这两条版本序列相互独立。cube 原语中的 v9 不代表正常世界已经使用 cube-grid。
4. 火山“完全没有热伤害实现”的说法已经过时：当前已有只读热暴露和玩家热伤害累计指标，但不是完整的生命值、死亡及跨进程持久化闭环。
5. 角色受力、结构承载和生存需求存在独立模型与单测；不能据此认定正常玩家已经具备完整生存玩法、建筑支撑图或坍塌系统。
6. 原路线图 01–16 阶段的 Complete 是对历史限定范围的结项，不是对当前完整游戏的认证。
7. 之前给出的整体 75%–80% 和各模块百分比没有统一验收项分母，**不作为本报告的可核验结论**。

证据入口：[当前路线图](<../todo/00-roadmap.md#L7-L38>)、[版本常量](<../src/world/terrain_generation.h#L7-L10>)、[默认拓扑](<../src/world/surface_topology_version.h#L25-L27>)、[存档契约](<../src/world/save_format.h#L25-L31>)、[玩家热暴露接线](<../src/app/game_ecology.c#L257-L268>)。

## 2. 完成度的评估口径

### 2.1 先明确三类范围

| 范围 | 含义 | 可以怎样下结论 |
| --- | --- | --- |
| 当前开发版能力 | 现有正常游戏路径和已经承诺的有界模型 | 判断已实现、已接入、已验证的能力 |
| 当前改造目标 | cube-grid、相关消费者、V30 和极区验收 | 按完整转换闭环判断，不能只看原语测试 |
| 后续扩展设想 | 全球输运、完整生存、动物热危害等 | 若未纳入本阶段，不因未做而给本阶段扣分 |

不能把未来的全部设想加入分母，也不能为了提高完成度把本阶段必要集成排除在分母外。

### 2.2 建议采用的五项标准

以下权重是**建议的后续管理规则**，不是仓库现有的官方评分，也不是对之前百分比的事后证明。

| 维度 | 建议权重 | 达标条件 |
| --- | ---: | --- |
| 功能实现 F | 30% | 冻结范围内的行为已经实现，不是空接口、占位或单独演示 |
| 生产集成 I | 25% | 正常游戏调用，输入/输出、状态归属、维度切换和存档边界接通 |
| 正确性 C | 20% | 核心不变量、异常输入、容量拒绝、失败恢复及关键边界通过 |
| 性能资源 P | 10% | 在约定硬件、分辨率、距离和负载下满足帧时间、内存和队列预算 |
| 验收证据 V | 15% | 对应提交有可重复测试、必要的游戏内图形验收和同步文档 |

如将来需要数字：先为每个维度建立带 ID 的验收项，每项记为满足、部分、未满足或未验证；预先固定“部分”的计分方式。F/I/C/P/V 分别为各维度的 0–1 达成比例，按 `S = 30F + 25I + 20C + 10P + 15V` 得到阶段评分，并同时报告硬门槛状态。未知项不能默认通过，必须单列未知比例或评分区间。

项目总分还需要事先确定组件/工作包的工作量权重；不能简单平均七个组件分数，也不能再把重叠的八个功能分组加进去。

本次尚没有经确认的完整验收分母、统一性能预算和全套图形结果，因此不计算看似精确的组件或项目总分。

### 2.3 不可被加权总分掩盖的硬门槛

- 主流程未接入：只能称“模型/基础实现完成”或“集成中”。
- 核心身份、物质守恒、碰撞或数据安全失败：不能称该目标已完成。
- CPU 测试通过：不能替代 GPU、遮挡、覆盖和视觉验收。
- 已知极区覆盖缺陷仍开放：不能宣称无缝球面地表已完成。
- 当前没有对应验证：不能把历史测试结果写成当前版本通过。
- 100% 只表示**指定阶段范围完成**，不表示没有任何缺陷或以后无需开发。

仓库已有相近的[共同验收规则](<../todo/00-roadmap.md#L69-L78>)，但没有统一的百分比算法。

仓库实际有七个静态链接的所有权组件。前面讨论的八部分是产品功能分组，不是八个可独立加总的代码组件。

| --- | ---: | --- | --- |
| core | 13 / 16 | 时钟、DSL、插件宿主、原子 I/O、中性值类型和诊断 | 基础设施已接入；发布级验证另计 |
| world | 77 / 62 | 地形、区块、流体、天气、水文、地质、表面编辑 | 旧网格主线已有；cube 新路径部分集成 |
| space | 26 / 29 | 星系、轨道、天体参数、空间坐标及表面上下文 | 探索主链路已有；不等于全尺度统一物理空间 |
| ecology | 19 / 14 | 区域生态、营养、种群、谱系、实体行为和姿态 | 有界运行时已接入；cube 消费者转换待完成 |
| gameplay | 15 / 16 | 玩家、交互、背包、飞船、相册和地图标记 | 基础玩法已接入；扩展物理模型接入不足 |
| presentation | 37 / 35 | 地面/太空渲染、天气视觉、UI、音频和姿态派生 | 展示路径已有；新网格全路线视觉/性能待验收 |
| app | 42 / 39 | 游戏循环、设置、持久化编排、世界切换、DSL 接线 | V29/旧网格编排已有；新拓扑闭环尚未收口 |

统计为该代码基线的受版本管理源文件：共 229 个 C 文件、211 个头文件；文件数只说明规模，不用于计算完成度。受版本管理的 DSL 场景为 48 个，也不等于 48 个当前已经通过的验收项。

组件定义和边界见[构建清单](<../mk/components.mk#L1-L28>)、[组件所有权记录](<architecture/13-component-build-boundaries.md#L27-L74>)。

### 3.1 主要数据流

```text
app：输入 / 设置 / 固定步时钟 / 世界切换
  ├─ gameplay：移动、飞船、交互与库存事务
  ├─ space：时间、轨道、天体与表面身份
  ├─ world：地形、区块、流体、天气、水文与地质
  └─ ecology：区域状态、实体与行为
                 ↓ 只读值、快照、姿态和中性效果
            presentation：画面、UI、音频

app：汇集各子系统状态 → 存档事务 → 文件
core：为上述路径提供中性基础设施，不反向依赖高层组件
```

后台生成与网格任务使用受控输入和生命周期；GPU 上传在主线程。组件可独立重建不代表完全没有跨组件调用，现有构建仍用链接组组合七个归档。也不能由架构检查通过推断所有模块耦合问题均已消除。

## 4. 七个组件的详细评估与退出标准

### 4.1 core：基础设施

**已有能力**

- 显式固定步时钟、有限追赶预算和输入回放。
- DSL 解析、stdin block 协议、错误回复和调试控制。
- ABI v2 插件生命周期、确定性加载顺序和版本化只读服务。
- 原子写入、旧文件备份和读取事务回滚。

证据：[时钟契约](<../src/core/simulation_clock.h#L10-L84>)、[插件 ABI](<../src/core/plugin.h#L8-L31>)、[原子 I/O 与回滚](<../src/core/save_io.c#L80-L145>)。

**本阶段完成标准**

1. core 无高层域头依赖，公共头可独立编译。
2. 时钟和回放的有限输入、顺序、容量和确定性测试通过。
3. 插件加载失败可回收已获得资源，服务生命周期不悬空。
4. 写入失败不破坏主文件，读取失败有明确回滚结果。
5. DSL 无窗口协议测试通过；实际游戏控制另有图形集成测试。

**剩余与限制**：单测覆盖不等于磁盘突然掉电、所有平台和任意第三方插件均安全；回放测试也不是整个游戏任意时刻的完整状态重放认证。原生 `.so` 插件是受信任的进程内扩展，不是安全沙箱；只读服务接口不会阻止恶意原生插件破坏进程。

### 4.2 world：世界、地形和模拟

**已有能力**

- 程序化地形、洞穴、矿物、河湖、地貌、区块与网格后台生成。
- 天气、辐射、水文、野火、龙卷风和火山/熔岩/灰烬的有界运行时。
- CGA 结构生成已接入正常 Homeworld 非平坦地形，不只是预览。
- cube 坐标、共享几何、生成上下文、编辑存储、任务适配、覆盖准入与投影网格。

**主要未完成目标**：cube 相关消费者统一转换、正常调度启用、共享覆盖策略、V30、极区与跨面实景验收。详见第 5 节。

**本阶段完成标准**

1. 一个方块在生成、编辑、碰撞、选取、流体和存档中具有相同身份。
2. 跨面和角点邻接可逆；位置、速度与朝向转换一致。
3. 地形、流体及地质状态尊重各自物质/能量和容量边界。
4. 调度、保留、LOD 与绘制对实际投影覆盖有一致定义，饱和时明确降级。
5. 正常路线可跨极点、挖放、离开重返和存读档，画面无已知覆盖缺陷。
6. 对实际激活路径完成性能与内存验收，而不只测独立原语。

证据：[cube 现状](<surface-cube.md#L3-L12>)、[地貌视觉缺陷](<landform-quality.md#L70-L103>)、[历史地质 V11](<volcanic-activity-design.md#L278-L307>)、[CGA 边界](<architecture/19-cga-voxel-grammar.md#L89-L94>)。

### 4.3 space：星系、轨道和表面转换

**已有能力**：确定性星系与天体参数、轨道和光照、查询缓存、空间区块，以及 Homeworld/行星的着陆与起飞编排。

证据：[星系生成与查询](<../src/space/space_runtime.c#L25-L96>)、[轨道求值](<../src/space/space_runtime.c#L135-L168>)、[着陆和起飞](<../src/app/game_world_transition.c#L80-L179>)。

**本阶段完成标准**

1. 同一世界种子与天体身份导出一致的轨道、物理参数、外观和表面种子。
2. 地面→太空→目标行星→地面的主链路可重复，目标移动或无固体表面时明确拒绝。
3. 转换中的坐标、速度、朝向、飞船和存档状态正确。
4. 缓存和空间流式在长距离与重定位后不串世界、不重复身份。
5. 正常游戏和真实图形路线通过，而非仅数值轨道测试通过。

**边界**：轨道空间和着陆后的体素表面采用不同参考尺度，不是同一个真实天体半径下的一米体素空间；这是当前显式设计，不应自动算作缺陷。见[单位契约](<../src/space/space_units.h#L6-L15>)。cube 接入后仍需重验表面进出链路。

### 4.4 ecology：生态、实体与演化

**已有能力**：区域营养与种群、迁移与基因流、有限谱系、历史状态保存、实体出生死亡反馈、行为与姿态；正常固定步已有区域和实体接线。

证据：[固定步接线](<../src/app/game_ecology.c#L214-L251>)、[动物姿态及已知限制](<architecture/17-fauna-poses.md#L74-L83>)、[生态阶段记录](<architecture/03-ecology-nutrients.md>)。

**本阶段完成标准**

1. 区域及谱系身份与表面隔离，切换天体不串状态。
2. 营养和种群满足模型不变量，容量不足不静默丢弃历史。
3. 活动/离屏状态推进符合约定，缓存淘汰和存读档保留必要历史。
4. 出生、死亡与区域人口反馈一致；渲染不反向修改模拟或消耗随机序列。
5. cube 下的位置、地面查询和生态装饰接通；帧时间预算经实测确认。

**容量与连续性**：生态区域边长 64，hot cache 为 256 组×4 路，即 1024 个记录；hot+cold 总记录上限为 65536，每区最多八个谱系。淘汰会保留历史，满容量/分配失败时拒绝新接纳而不是静默抹掉旧历史。不是所有已存记录都每 tick 同时演化。历史补算对未记录的人工干预有明确重建限制，不能宣称重放了全部过去事件。见[容量常量](<../src/ecology/ecology_internal.h#L8-L21>)和[连续性范围](<architecture/16-ecology-continuity.md>)。

**边界**：动物姿态是运动学与局部避障，不是布娃娃或完整空气动力学；采食饮水主要使用生态可用性，并非一定消耗某个具体植物/水体素。完整全球生态不是当前有界模型的验收前提。

### 4.5 gameplay：玩法、交互和载具

**已有能力**：玩家碰撞/游泳、射线与挖放、库存和薄层定量采集、飞船控制、相册、地图标记等。

证据：[玩家碰撞坐标](<../src/gameplay/player.c#L69-L104>)、[射线输入防护](<../src/gameplay/interaction.c#L25-L71>)、[定量采集事务](<../src/gameplay/inventory.c#L26-L37>)。

**本阶段完成标准**

1. 移动与碰撞、相机和选取对应同一几何；高速和边界位置不穿透。
2. 放置和采集的世界/库存事务一致，失败不复制或吞掉物品。
3. 门、楼梯、半高块、液体和地质薄层的交互符合实际形状。
4. 飞船进出、表面转换和保存恢复在同一身份体系下工作。
5. 玩家输入路径实际使用 cube 几何与地址，并通过跨面/极点交互验收。

**需要区分的范围**：角色受力、结构承载、生存需求的独立模型不能等同完整生产玩法。若后续目标包含坍塌或生存，需要另行实现支持关系图、状态所有者、玩家接线及持久化，不能只把现有模型测试标成玩法完成。

### 4.6 presentation：画面、UI 和音频

**已有能力**：地面/太空/Nether 的环境派生、地形材质、水和阴影、天气、动物姿态、火山 overlay、UI 与环境音频；质量档位有明确资源配置。

证据：[环境派生输入](<../src/presentation/environment_runtime.c#L14-L67>)、[质量档位](<../src/presentation/render_quality.c#L3-L49>)、[cube 渲染变换与包围体](<../src/presentation/surface_render_transform.c#L5-L57>)。

**本阶段完成标准**

1. 渲染只消费模拟状态，不写回权威状态或制造随机顺序差异。
2. 地形、液体/岩层 overlay、阴影、选中框和碰撞几何对齐。
3. 跨面、极点、高空、不同视距和 LOD 没有错误裁剪或不合理覆盖缺口。
4. GPU 资源创建/失败/释放可控，降级行为明确。
5. 在约定场景完成视觉审查、GPU/CPU 帧时间和资源稳定性验收。

**当前不能宣称的内容**：本次无真实图形重验；无窗口单测中的 shader 降级通过不等于真实 GPU 路径通过；曾有平坦静态/旋转性能样本也不能代表高视距、火山、复杂建筑或新网格负载。

### 4.7 app：组合根、生命周期和持久化

**已有能力**：输入、固定步调度、环境快照、世界切换、存档/设置、调试报告和插件服务编排。

证据：[运行时所有者](<../src/app/game_runtime.h#L60-L85>)、[固定步顺序](<../src/app/game_ecology.c#L195-L216>)、[切换前排空及快照安装](<../src/app/game_world_transition.c#L21-L37>)、[存档状态](<../src/app/game_save.c#L54-L69>)。

**本阶段完成标准**

1. 每类状态有明确 owner，切换前排空任务，旧结果不能污染新世界。
2. 新建、暂停、返回菜单、着陆、起飞、读档、失败回滚和退出均有明确生命周期。
3. V30 与 cube 地址一起完整序列化；错误格式拒绝，不迁移或删除旧文件。
4. 载入时对临时状态校验后提交，失败恢复 live game。
5. DSL 状态与实际游戏路径一致，报告有身份/帧/tick 关联，文档与默认版本同步。

**主要差距**：新拓扑编排和持久化闭环未完成；当前源码、路线图与部分架构说明的版本/能力叙述不同步。

### 5.1 不能忽略的容量和形变风险

- 本次 cube CPU 测试输出：16 格边的样本实际长度为 **9.628–20.371** 物理单位；这是受控投影形变，不是全局等尺寸正方体。
- 覆盖测试输出的最大请求为 **1560** 列，现有槽位预算记录为 **625**；特定极端请求会饱和。必须决定优先级、实际视距和降级策略，不能默默把部分覆盖标成完整。
- 图距离不等于物理距离；角点移动顺序不能默认交换。
- 局部 `surface_ready` 不等于全视锥可见地面已经齐全。

因此，是否改进投影应通过样本指标小范围比较；现阶段没有实测证据证明换成另一种网格可以直接消除集成工作。

## 7. 模拟能力的真实边界

### 7.1 辐射与水文

当前是有界活动区域模型，不是全星球同时求解的气候/海洋系统，且两个运行时不能笼统描述为同一种 128×128 网格：

- **辐射**：在一个 128×128 canonical 区域身份下维护一份辐射柱状态，不是为区域内每格各求解一根柱；切换区域/表面会重新绑定并初始化。温度偏移反馈只对匹配的活动区域有效。
- **水文**：一份覆盖 128×128 区域、32×32 粗格、每格默认 4 米的求解器；地形和降水有分批采样，切换区域会重新初始化，不像生态那样保留所有访问流域的历史。
- **静态地貌**：全球排水图谱用于生成基底，不等于动态全球水系。M0–M3 已交付，M4 目前只有河流阶地；曲流、牛轭湖、海岸等扩展和 M5 局部动态沉积仍未交付。

区域间热输运、动态全球河流输运、海洋输运、离屏流域集成等没有因为阶段标记 Complete 而自动实现。若将来要宣称这些能力，需新增跨区状态、通量、预算和持久化验收；它们未进入当前阶段时也不应直接扣分。

证据：[辐射状态布局](<../src/world/radiation_runtime.h#L15-L67>)、[水文尺度](<../src/world/hydrology_runtime.h#L10-L17>)、[范围声明](<architecture/README.md#L67-L72>)、[地貌分阶段范围](<geographic-landforms-design.md#L150-L182>)。

### 7.2 火山热暴露与“伤害”的精确含义

当前生产固定步会读取热暴露，并在天气伤害开关开启时累计 `playerHeatDamage` 到 0–1；关闭开关冻结累计但不隐藏热暴露。

不能把该指标等同成熟的玩家生命值系统：当前玩家类型没有生命值/生存状态；尚无由该累计量驱动玩家死亡的完整链路。已有 DSL 对同一进程内 save/load 的保持检查，不等于跨进程持久化验证。新动态熔岩 overlay 的热源点燃不能用旧静态 `BLOCK_LAVA` 点燃路径代替。

证据：[较新 P1 记录](<volcanic-activity-design.md#L631-L636>)、[生产累计逻辑](<../src/app/game_ecology.c#L257-L268>)、[玩家状态](<../src/gameplay/player_types.h#L11-L20>)、[场景断言](<../tests/scenes/volcano_heat_exposure.dsl#L23-L36>)、[旧静态熔岩点火](<../src/world/weather_impact.c#L819-L836>)。

### 7.3 角色、结构与生存

独立模型已有不等于生产世界会发生支撑传播、建筑坍塌、脱水或体温致死。当前应把它们分别标为模型能力和后续玩法集成，不能笼统称“完整物理/生存系统完成”。见[模型范围](<architecture/05-character-structure-physics.md#L3-L22>)。

### 7.4 确定性回放与固定步

环境系统和实体已有生产固定步接线，但玩家运动与龙卷风对玩家施力仍先按渲染帧更新，一帧内的多个模拟 tick 共享该帧玩家位置。因此不能把“固定步模型和环境测试通过”写成“全游戏已消除帧率差异”。见[生产帧调度](<../src/app/game.c#L1180-L1204>)。

现有跨系统回放是受控、加载场景下的时钟/天气/生态/水/火比较，不是 GPU、全部生产输入、区块卸载或任意中途流体存档的确定性认证。见[回放持久化及排除范围](<architecture/14-cross-system-replay.md#L46-L73>)。

### 7.5 灾害兼容运行时与独立物理模型

正常游戏已有野火、龙卷风及实体危害，生产调度会调用天气影响、龙卷风和实体伤害路径。但独立的 `HazardFireStep` / `HazardSupercellStep` 在生产 C 文件中只找到自身定义，没有发现上层消费者，不能把其 SI 物理模型测试视为已经替换生产火灾/超级单体行为。

野火推进也受活动表面与已加载区域限制，不是离屏全球持续蔓延；龙卷风不是一套完整多块刚体坍塌系统。证据：[正常灾害接线](<../src/app/game_ecology.c#L232-L251>)、[独立物理模型边界](<architecture/04-hazard-physics.md>)、[当前天气模拟范围](<weather-simulation.md>)。

## 10. 推荐推进顺序与阶段退出条件

优先级是对“完成新网格开发版”目标的建议，不是已复现的安全漏洞评级；不提供没有估算基础的人日或发布日期。

| 阶段 | 范围与依赖 | 退出条件 |
| --- | --- | --- |
| M0：冻结契约 | 明确当前 v11、cube 采样/历史层版本、V30 数据范围和覆盖预算；可并行做文档纠偏 | 版本、身份、所有者、容量及验收清单一致，无含混默认值 |
| M1：最小 cube 游戏闭环 | 复用已有原语/队列，建立使用正常游戏逻辑的受控实验路径，接玩家、碰撞、射线、挖放和覆盖 | 小星球跨一个接缝与角点，挖放、离开返回正确；不靠绕开正常逻辑的 debug 演示代替 |
| M2：持久化闭环 | 在 M1 身份契约稳定后完成 V30 和旧格式拒绝；不保留兼容迁移负担 | 跨面编辑在重新进程加载后保持；坏文件/旧格式拒绝且原文件及 live game 完整 |
| M3：消费者统一 | 流体、生态装饰、实体地面查询、火山/灰层等依赖 M1/M2 地址和几何 | 各生产消费者不再用旧 map 坐标解释 cube 单元，跨面物质与状态一致 |
| M4：全覆盖与性能验收 | 调度/保留/LOD/绘制统一，明确饱和降级；跑湿/干极区、高空和多视距路线 | 画面通过；内存/CPU/GPU/队列在冻结预算内；不以局部 ready 冒充覆盖 |
| M5：发布候选收口 | 同一候选提交运行 normal、sanitizer、GCC/Clang、图形和发布门禁 | 原始证据可重放，关键缺陷关闭，已知范围和文档同步 |

阶段实验必须隔离运行，完成所有启用门槛前不切换普通默认拓扑，也不把实验 cube 状态伪装成 V29 的 legacy 数据。每完成一个阶段单独提交，并同步当前状态文档。

M0 中可以做小规模等角/低畸变投影对照，但只有测量证明现有投影不能满足目标时才扩大变更。当前没有证据支持为了“更先进”而先替换整个网格拓扑。

不建议此时优先扩大完整全球气候、板块、布娃娃、复杂坍塌或更多独立建筑风格；它们不能替代当前坐标与持久化收口。

## 11. 风险清单与后续报告格式

| 风险 | 影响 | 控制方法 |
| --- | --- | --- |
| 新旧坐标混用 | 看见、碰撞、流体与保存指向不同方块 | 单一方块身份契约、转换集中、跨面真实路线 |
| 容量不足被误报为就绪 | 极区/高空缺地面、交互与画面不一致 | 请求/接纳/就绪分开统计，冻结预算和降级政策 |
| 生成版本与缓存输入不完整 | 相同身份产生不同基底或读档结果 | 显式捕获版本、排空任务、复现指纹和重载测试 |
| 模型完成冒充玩法完成 | 进度虚高、实际闭环缺失 | 源码/生产调用/当前验收三轴报告 |
| 文档滞后 | 错估版本与功能缺口，重复或错误开发 | 每阶段更新当前状态入口并单独提交 |
| 旧或局部性能样本外推 | 新网格/高视距下超帧或超内存 | 固定硬件、场景、距离、worker 与三次同机基准 |
| 只测正常用例 | 保存失败、队列拒绝和资源失败损坏状态 | 故障注入、边界及事务测试，并保留异常结果 |

后续每次进度更新建议固定报告：`目标范围 → 验收项 ID → 实现状态 → 生产接入状态 → 验证命令/提交/日期 → 剩余项 → 阻断项`。有明确任务权重和范围之后再计算百分比，禁止用代码行数、提交数或测试数替代产品完成度。

**最终判断：底层能力与内容积累已经相当可观，最重要的剩余工作是让新球面网格、全部消费者和持久化成为同一条正常游戏路径，并在该路径上完成图形与性能验收，而不是继续堆叠互相独立的功能。**
